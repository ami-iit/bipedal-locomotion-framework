# Robot log format `v0.1.0`

This document specifies the format `v0.1.0` of the robot logs. It is written by the [`YarpRobotLoggerDevice`](../../README.md) of `bipedal-locomotion-framework` `v0.29.0` or newer. See [README.md](./README.md) for the versioning of the format, and [v0.0.1.md](./v0.0.1.md) for the previous format.

A log is composed of:
- a [`.mat` file](#the-mat-file) containing all the numerical and textual signals;
- optionally, one [video or image folder](#videos-and-images) per camera stream, in the same folder of the `.mat` file.

## Changes with respect to `v0.0.1`
- The top-level variable [`version`](#top-level-variables) contains the version of the format.
- [`yarp_robot_name`](#root-struct) contains a URI of the robot model, resolvable with [`resolve-robotics-uri-py`](https://github.com/ami-iit/resolve-robotics-uri-py), instead of the value of the `YARP_ROBOT_NAME` environment variable.
- The [camera channels](#cameras) store the index and the time of every saved image, also when the images are stored in a video. The index restarts from zero in each file.
- The rgb videos are H.264 fragmented `.mp4` files with variable frame rate, whose presentation time is the logging time. The depth videos are lossless 16 bit `.mkv` files instead of 8 bit `.mp4` files.
- New [`exogenous_signals_connection_id`](#exogenous-signals) channels, and `_connection_<k>` channels for exogenous signals whose structure changed after a reconnection.

## File names
All the files of a log share the same base name `<prefix>_<YYYY>_<MM>_<DD>_<hh>_<mm>_<ss>`, where the date is the local time of the save, and `<prefix>` is `robot_logger_device`, or `robot_logger_device_<tag>` if the recording is saved with a tag (see the `saveRecording` and `saveAndStopRecording` rpc commands of the device).

| File | Content |
|:---|:---|
| `<base>.mat` | [The mat file](#the-mat-file). |
| `<base>_<camera>_rgb.mp4` | Color images of the camera `<camera>` (save mode `video`). |
| `<base>_<camera>_depth.mkv` | Depth images of the camera `<camera>` (save mode `video`). |
| `<base>_<camera>_<rgb\|depth>/img_<k>.png` | Images of the camera `<camera>` (save mode `frame`). |
| `<base>_<signal>_rgb/img_<k>.png` | Images of the exogenous image signal `<signal>`. |
| `<base>_*.txt` | Output of the `code_status_cmds` commands (e.g., the status of the repositories), if configured. |

When the logger saves the data periodically (`Telemetry/save_period`), every save produces a new `.mat` file together with its own videos and image folders, covering the time elapsed since the previous save.

While recording, the images are written in files named `output_<camera>_<rgb|depth>.<ext>` that are renamed when the log is saved. If the logger is not closed properly, these files are left in the log folder; the rgb `.mp4` files can be read anyway, since they are fragmented. They are renamed `output_<camera>_<type>_recovered_<date>.<ext>` when the logger starts again.

## The mat file
The file is a MATLAB `v7.3` file, i.e., an HDF5 file. It can be loaded with `load` in MATLAB, and with [`h5py`](https://www.h5py.org/) or [`mat73`](https://github.com/skjerns/mat7.3) in Python.

### Top-level variables
| Variable | Type | Content |
|:---|:---|:---|
| `version` | char array | Version of the format, `0.1.0`. |
| `<prefix>` | struct | [Root struct](#root-struct) of the log. Its name is the `<prefix>` of the [file name](#file-names), i.e., `robot_logger_device` unless the log has been saved with a tag. |

A reader should not rely on the name of the root struct: it is the only top-level struct, and it contains the `yarp_robot_name` field.

### Root struct
| Field | Type | Content |
|:---|:---|:---|
| `yarp_robot_name` | char array | URI of the robot model, set with the `robot_model_uri` parameter of the device, e.g., `package://ergoCub/robots/ergoCubSN001/model.urdf`. Any URI supported by [`resolve-robotics-uri-py`](https://github.com/ami-iit/resolve-robotics-uri-py) can be used. Empty if the parameter is not set. |
| `description_list` | `n x 1` cell array of char arrays | Names of the logged joints, in the order used by all the joint channels. Present only if the robot data is logged. |
| other fields | struct | The [channels](#channels), organized in a tree. |

### Channels
Each signal is stored in a channel. The name of a channel is a list of keys separated by `::`, e.g. `joints_state::positions`, and it is stored as nested structs, e.g. `robot_logger_device.joints_state.positions`. Since the keys are names of MATLAB struct fields, they contain only letters, numbers and underscores (the character `-` is replaced with `_` in the text logging channels).

Each leaf is a struct with the following fields, where `N` is the number of samples of the channel:

| Field | Type | Content |
|:---|:---|:---|
| `data` | see below | The samples. |
| `timestamps` | `N x 1` double | Time of each sample in seconds, read from the YARP clock when the sample is logged (the simulation time if the YARP network clock is used). |
| `dimensions` | `3 x 1` uint64 | Size of `data`, e.g. `[n; 1; N]`. |
| `elements_names` | `1 x n` cell array of char arrays | Name of each element of a vector. If the producer does not provide them, they are `element_0`, `element_1`, .... |
| `units_of_measure` | `1 x n` cell array of char arrays | Always `n.d.`. |
| `name` | char array | Last key of the channel name, e.g. `positions`. |

The type of `data` depends on the channel:

| Channel type | `data` |
|:---|:---|
| vector of size `n` | `n x 1 x N` double array: `data(:, 1, k)` is the sample at `timestamps(k)`. **Note:** due to the HDF5 storage order, `h5py` returns an array of shape `(N, 1, n)`. |
| image index | `1 x 1 x N` uint32 array (see [cameras](#cameras)). |
| string | `1 x N` cell array of char arrays. |
| text log | `1 x N` struct array (see [text logging](#text-logging)). |

The channels do not share the time axis: each channel has its own `timestamps`, and its samples are logged only when a new value is available (e.g., an exogenous signal starts when its port is connected, a camera channel is updated at the rate of the camera). The robot channels are logged every `sampling_period_in_s` seconds (default `0.01`). A channel that has been created but that does not contain samples is stored as a struct without fields.

#### Robot
The robot channels are created according to the `stream_*` parameters of the `RobotSensorBridge` group. The values are in the units returned by the `YarpSensorBridge` of `bipedal-locomotion-framework` (e.g., the joint positions in radians).

| Channel | Elements | Enabled by |
|:---|:---|:---|
| `joints_state::positions`, `joints_state::velocities`, `joints_state::torques` | joints (`description_list`) | `stream_joint_states` |
| `joints_state::accelerations` | joints | `stream_joint_states` and `stream_joint_accelerations` |
| `motors_state::positions`, `motors_state::velocities`, `motors_state::accelerations`, `motors_state::currents` | joints | `stream_motor_states` |
| `motors_state::temperatures` | joints | `stream_motor_states` and `stream_motor_temperature` |
| `motors_state::PWM` | joints | `stream_motor_PWM` |
| `PIDs` | joints | `stream_pids` |
| `FTs::<sensor>` | `f_x`, `f_y`, `f_z`, `mu_x`, `mu_y`, `mu_z` | `stream_forcetorque_sensors` |
| `gyros::<sensor>` | `omega_x`, `omega_y`, `omega_z` | `stream_inertials` |
| `accelerometers::<sensor>` | `a_x`, `a_y`, `a_z` | `stream_inertials` |
| `orientations::<sensor>` | `r`, `p`, `y` | `stream_inertials` |
| `magnetometers::<sensor>` | `mag_x`, `mag_y`, `mag_z` | `stream_inertials` |
| `cartesian_wrenches::<name>` | `f_x`, `f_y`, `f_z`, `mu_x`, `mu_y`, `mu_z` | `stream_cartesian_wrenches` |
| `temperatures::<sensor>` | `temperature` | `stream_temperatures` |
| `batteries::<battery>` | `voltage`, `current`, `charge`, `temperature` | `stream_battery` |

#### Frames
If `log_frames` is enabled, the pose of each frame published on the YARP transform server (configured in the `Transforms` group) with respect to one of the `parent_frames` is stored in:

| Channel | Elements |
|:---|:---|
| `frames::<parent>::<frame>::position` | `x`, `y`, `z` |
| `frames::<parent>::<frame>::orientation` | `qx`, `qy`, `qz`, `qw` (unit quaternion) |

#### Exogenous signals
The exogenous signals are the signals streamed by other applications and listed in the `ExogenousSignals` group. In the following, `<signal>` is the `signal_name` of the signal.

| Input type | Channel | Content |
|:---|:---|:---|
| `vectors_collection_exogenous_inputs` | `<signal>::<key>` | One vector channel for each key of the `VectorsCollection`. The key can contain `::`, and the elements names are the metadata provided by the `VectorsCollectionServer`. |
| `vectors_exogenous_inputs` | `<signal>` | Vector channel with elements `element_<i>`. |
| `string_exogenous_inputs` | `<signal>` | String channel containing the content of the received bottles. |
| `human_state_exogenous_inputs`, `wearable_targets_exogenous_inputs`, `wearable_data_exogenous_inputs` | `<signal>::...` | Vector channels obtained by converting the `trintrin` messages. |
| `image_exogenous_inputs` | `exogenous_images::<signal>::rgb` | Image index channel, the images are stored in the folder `<base>_<signal>_rgb` (see [cameras](#cameras)). |
| all, except images | `exogenous_signals_connection_id::<signal>` | Vector channel with the element `connection_id`, logged with every sample of the signal. It is the index of the connection to the port that produced the sample: `1` for the first connection, `2` after the first reconnection, and so on. |

If after a reconnection the size or the elements names of a vector change, the new samples are stored in the channel `<channel>_connection_<k>`, where `k` is the index of the connection.

#### Cameras
For each camera listed in the `RobotCameraBridge` group (or found in the attached devices), the following channels are created:

| Channel | Elements | Cameras |
|:---|:---|:---|
| `camera::<camera>::rgb` | `frame_index` | rgb and rgbd cameras |
| `camera::<camera>::depth` | `frame_index` | rgbd cameras |

A sample `(timestamps(k), data(1, 1, k))` states that the image with index `data(1, 1, k)` in the video (or in the frames folder) associated to the `.mat` file has been acquired at time `timestamps(k)`. The index starts from zero in each file, hence the time of the first image of `<base>_<camera>_rgb.mp4` is the time associated to the index `0` in `<base>.mat`. Only the images actually written are logged, so a dropped image does not shift the following ones.

#### Text logging
If `log_text` is enabled, the messages of the YARP loggers whose port name matches `text_logging_subnames` are stored in the channels `<system>::<prefix>::<process>::p<pid>`, e.g. `log::balancing::balancing_controller::p12345`, where the character `-` is replaced with `_`. The data is a struct array with one element for each message, with the fields `level`, `text`, `filename`, `line`, `function`, `hostname`, `cmd`, `args`, `pid`, `thread_id`, `component`, `id`, `systemtime`, `networktime`, `externaltime`, `backtrace`, `yarprun_timestamp` and `local_timestamp`.

## Videos and images
Each camera stream is saved according to its save mode (`rgb_cameras_rgb_save_mode`, `rgbd_cameras_rgb_save_mode`, `rgbd_cameras_depth_save_mode`):

| Stream | Save mode `video` | Save mode `frame` |
|:---|:---|:---|
| color | `<base>_<camera>_rgb.mp4`: H.264 (`libx264` by default, otherwise `libopenh264` or `mpeg4`, see `video_encoder`), `yuv420p`, fragmented mp4. An image with an odd width or height is cropped to an even size. | `<base>_<camera>_rgb/img_<k>.png`, 8 bit color. |
| depth | `<base>_<camera>_depth.mkv`: lossless FFV1, `gray16le`. | `<base>_<camera>_depth/img_<k>.png`, 16 bit grayscale. |

The images of the exogenous image signals are always saved in frame mode, as 8 bit color png files.

- **Depth values.** The depth images contain `round(depth * scale)` saturated to `uint16`, where `depth` is the depth in meters and `scale` is the `rgbd_cameras_depth_scale` parameter of the camera (default `1000`, i.e., millimeters). The value `0` means that the depth is not available.
- **Time.** In the video files, the presentation time of each image is the logging time of the image minus the logging time of the first image (variable frame rate), so the time of the image with index `k` is `<presentation time> + <first image time>`, where the time of the first image is stored in the container metadata `blf_first_frame_time` (seconds, the `.mkv` muxer stores the key in upper case) and in the camera channel. The videos have no B-frames and a keyframe every two seconds. In the frame mode, `img_<k>.png` is the image with index `k` of the camera channel.

## Real-time streaming
If `enable_real_time_logging` is `true`, the vector channels are also streamed by a `VectorsCollectionServer` (by default on the port `<port_prefix>/rt_logging`). This stream is not part of the format of the files, but it uses the same names: each channel `<channel>` is streamed with the key `robot_realtime::<channel>`, and the metadata contain `robot_realtime::yarp_robot_name` (a single element: the URI of the robot model), `robot_realtime::description_list` and `robot_realtime::timestamps`. The string, text and image index channels are not streamed, and the stream does not contain the format version.

## Visualization with `robot-log-visualizer`
The [`robot-log-visualizer`](https://github.com/gbionics/robot-log-visualizer) reads `version` to know how to interpret the file. For logs in the format `v0.1.0`:

- **Robot model.** The model is loaded by resolving `yarp_robot_name` with [`resolve-robotics-uri-py`](https://github.com/ami-iit/resolve-robotics-uri-py), and the joints are matched by name with `description_list`. The model and the package folder can also be set manually before opening the file.
- **Videos.** All the files named `<base>_*.mp4` and `<base>_*.mkv` in the folder of `<base>.mat` are opened in a tab. They are synchronized with the other signals using the time of the image with index `0` in `camera::<camera>::<rgb|depth>`. If the channel is not available, the video is assumed to span the entire log. The frames folders are not displayed.
- **Depth videos.** The 16 bit depth videos are displayed with the `turbo` colormap between `0.2 m` and `5.0 m` (assuming a scale of `1000`), and the pixels without depth (value `0`) are black. A colorbar is shown below the image.
- **Images streamed as numerical signals.** An image streamed as a vector (e.g., the depth image seen by a policy, streamed through a `VectorsCollectionServer`) can be displayed as an image: right click on the channel in the variables tree and select *Render as image*. The option is available if the last key of the channel name contains `image` or `img` (case insensitive) and either all the elements are named `r<row>_c<col>` (the size of the image is obtained from the names, the elements can be in any order), or the number of elements is a perfect square (a square image stored row by row is assumed). The values are displayed with the `turbo` colormap between `0` and `1`, a range that is enlarged to include the minimum and maximum values of the signal, and the value `0` is black. The same works with the real-time streaming. A producer that wants to stream an image should therefore name the channel `.../<something>_image` and the elements `r<row>_c<col>`.
